# อีเมลผ่าน Brevo

ใช้ Brevo Transactional Email API (`POST /v3/smtp/email`) ไม่ต้องตั้ง SMTP

## ตั้งค่า

| ค่า | การใช้งาน |
| --- | --- |
| `BREVO_API_KEY` | คีย์ที่มีสิทธิ์ส่ง Transactional Email |
| `BREVO_SENDER_EMAIL` | อีเมลผู้ส่งที่ยืนยันใน Brevo แล้ว |
| `MAIL_ENCRYPTION_KEY` | ค่าสุ่มลับคงที่สำหรับเข้ารหัสเนื้อหาในคิว แนะนำแยกจาก JWT secret |
| `app.frontend-url` | origin ของ FrontEnd เช่น `https://your-app.vercel.app` ใช้ทั้ง CORS และลิงก์ในอีเมล |
| `app.brevo.sender-name` | ชื่อผู้ส่ง ค่าเริ่มต้น MultiRole |
| `app.time-zone` | เขตเวลาของ deadline ค่าเริ่มต้น Asia/Bangkok |

สำหรับเครื่องนี้ ตั้งคีย์และผู้ส่งใน `config/application-local.properties` ซึ่ง Git ยกเว้นอยู่แล้ว ห้ามคัดลอกคีย์ลง FrontEnd หรือไฟล์ที่ commit สำหรับเครื่องอื่นใช้ environment variables ตามตาราง ควรเปลี่ยนคีย์ที่เคยเปิดเผยในแชตแล้วเก็บคีย์ใหม่ในที่เดียวกัน

ถ้าไม่กำหนด `MAIL_ENCRYPTION_KEY` ระบบใช้ JWT secret เป็นฐานสำหรับเข้ารหัสคิว การเปลี่ยนค่านี้ทำให้เนื้อหาอีเมลที่ยังอยู่ในคิวถอดรหัสไม่ได้ จึงควรกำหนดค่าคงที่แยกสำหรับ production และใช้ค่าเดียวกันทุก instance

## พฤติกรรม

- สมัครใหม่: สร้างบัญชีและคิวอีเมลใน transaction เดียวกัน ต้องกดยืนยันก่อน login ลิงก์ใช้ได้ครั้งเดียวภายใน 1 ชั่วโมง ไม่มีการยืนยันอัตโนมัติเมื่อเปิดหน้าเพื่อหลีกเลี่ยงโปรแกรมสแกนอีเมล
- บัญชีเดิม: คอลัมน์ `users.email_verification_required` เป็น null จึงไม่บังคับยืนยันย้อนหลัง แม้ `email_verified` เดิมเป็น false
- ส่งลิงก์ใหม่: เว้น 60 วินาที ยกเลิกลิงก์ก่อนหน้า ใช้คำตอบเดียวกันทั้งกรณีมี/ไม่มีบัญชี
- รีเซ็ตรหัสผ่าน: ลิงก์ใช้ได้ครั้งเดียวภายใน 30 นาที ส่งใหม่เว้น 60 วินาที ยกเลิกลิงก์ก่อนหน้า เปลี่ยนรหัสผ่านแล้วเพิ่ม `token_version` ทำให้ JWT เก่าใช้ไม่ได้
- เตือนประเมิน: ส่งทั้ง Notification ในเว็บและคิวอีเมล เฉพาะสมาชิก JUDGE/ADMIN_JUDGE ที่ ACTIVE และผ่านเงื่อนไขยืนยันบัญชี มีทีมที่มอบหมายค้างส่ง (DRAFT ยังถือว่าค้าง)
- กดเตือนเอง: ผู้ดูแลโครงการ/System Admin เท่านั้น เว้นอย่างน้อย 1 ชั่วโมงต่อกรรมการในโครงการเดียวกัน
- เตือนอัตโนมัติ: ตรวจทุก 60 วินาที เฉพาะโครงการ ACTIVE ที่เหลือไม่เกิน 24 ชั่วโมงและยังไม่ถึง deadline ส่งอัตโนมัติครั้งเดียวต่อโครงการ/กรรมการตลอดโครงการ แม้แก้ deadline ภายหลัง ทั้งสองช่องทางใช้ช่วงเว้น 1 ชั่วโมงร่วมกัน
- ไม่มี deadline, โครงการปิด/ร่าง, หมดเวลา, ประเมินครบ, ไม่มีทีมมอบหมาย หรือผู้ใช้ระงับ: ไม่สร้างอีเมลเตือน
- ก่อนส่งแต่ละครั้งตรวจสิทธิ์ สถานะและความเกี่ยวข้องอีกครั้ง หากไม่เกี่ยวข้องแล้วจะ CANCELLED การแจ้งเตือนในเว็บยังเก็บไว้
- การแจ้งเตือนชนิดอื่นไม่ถูกส่งเป็นอีเมล

## คิวและการแก้ปัญหา

Dispatcher ทำงานทุก 15 วินาที ครั้งละไม่เกิน 20 รายการ ใช้ lock ป้องกัน worker ส่งแถวเดียวกันพร้อมกัน ความล้มเหลวเครือข่าย/429/5xx จะลองใหม่ เว้น 1, 2, 4, 8, 16 นาที รวมสูงสุด 6 ครั้ง รหัส 4xx อื่นหยุดทันที ไม่มีการรับประกันส่งครั้งเดียวหากเกิดเครือข่ายขาดหลัง Brevo รับคำขอแล้ว

สถานะ `email_outbox`: PENDING, RETRY, ACCEPTED, FAILED, CANCELLED ส่วน Notification ใช้ QUEUED/RETRYING ระหว่างรอ ACCEPTED หมายถึง Brevo รับคำขอ พร้อมเก็บ `provider_message_id` ไม่ยืนยันการส่งถึงกล่องจดหมาย ควรตรวจ Transactional Logs ใน Brevo สำหรับการส่งจริง

Token เก็บเป็น SHA-256 ในตาราง token เนื้อหาอีเมลในคิวเข้ารหัส AES-GCM และล้างเมื่อรับคำขอสำเร็จ ยกเลิก หรือหยุดส่งถาวร ไม่พิมพ์ลิงก์ คีย์ หรือข้อความตอบกลับดิบของผู้ให้บริการลง log

```sql
SELECT status, COUNT(*) AS total FROM email_outbox GROUP BY status;
SELECT id, purpose, status, attempts, last_error, created_at, accepted_at
FROM email_outbox ORDER BY created_at DESC LIMIT 20;
```

หาก FAILED ให้แก้ค่าผู้ส่ง/คีย์/สิทธิ์ใน Brevo แล้วให้ผู้ใช้ขอลิงก์ใหม่หรือกดเตือนใหม่หลังช่วงเว้น ไม่มีการเปิด API แก้สถานะคิวให้ผู้ใช้ทั่วไป

การอัปเดต schema ใช้ Hibernate `ddl-auto=update` ตามการตั้งค่าเดิม เพิ่มตาราง `email_verification_token`, `email_outbox`, `evaluation_reminder`; เพิ่ม `users.email_verification_required`, `users.token_version` และ `notification.email_status` โดยไม่ยืนยันบัญชีเดิมย้อนหลัง ไม่ต้อง drop ตารางเดิม

## API

| API | สิทธิ์ |
| --- | --- |
| `POST /api/auth/resend-verification` `{email}` | Public คำตอบทั่วไป ไม่เผยว่ามีบัญชีหรือไม่ |
| `POST /api/auth/verify-email` `{token}` | Public ใช้ token ครั้งเดียว |
| `POST /api/auth/forgot-password` `{email}` | Public คำตอบทั่วไป |
| `POST /api/auth/reset-password` `{token,newPassword}` | Public ใช้ token ครั้งเดียว |
| `POST /api/notifications` `{competitionId,email}` | ผู้ดูแลที่มีสิทธิ์ในโครงการ ระบบกำหนดผู้รับและเนื้อหาจากฐานข้อมูล |

Login ด้วยรหัสถูกต้องแต่ยังไม่ยืนยันจะตอบ 403 พร้อม `code: EMAIL_NOT_VERIFIED` หน้าเว็บพาไป `/verify-email` โดยไม่สร้าง session

## ทดสอบ

`EmailWorkflowTests` ใช้ H2 และ HTTP mock ของ Brevo ตรวจสมัครใหม่/บัญชีเดิม การใช้ซ้ำ/หมดอายุ/ส่งใหม่ การยกเลิก JWT เดิม รูปแบบ API/HTML/คีย์ การลองส่งใหม่ คูลดาวน์ เงื่อนไขเตือนและคำขอพร้อมกัน Profile test ปิด scheduler และการส่งจริง ชุดทดสอบเก่าไม่บังคับยืนยันอีเมล ส่วนชุดอีเมลเปิดข้อกำหนดนี้โดยเฉพาะ

ตรวจเพิ่มเติมเมื่อ 25 ตุลาคม 2026: BackEnd เริ่มกับ MySQL และเพิ่ม schema สำเร็จ; Brevo ช่องทางส่งอีเมลตอบ 201 พร้อม receipt เมื่อใช้ `headers: {"X-Sib-Sandbox":"drop"}` ซึ่งไม่ส่งถึงผู้รับจริง การอ่าน account/senders ด้วยคีย์นี้ตอบ 403 เนื่องจากไม่มีสิทธิ์อ่าน resource account จึงยังตรวจสถานะผู้ส่งและการเข้ากล่องจดหมายจริงไม่ได้จากผลทดสอบนี้

ก่อนใช้งานจริงให้ตรวจผู้ส่งในหน้า Brevo และทดลองสมัครด้วยอีเมลที่รับได้ เพื่อทดสอบยืนยันบัญชีและรีเซ็ตครบวงจรผ่านกล่องจดหมาย การทดสอบโหมด sandbox ตรวจรูปแบบคำขอเท่านั้น

เอกสารทางการ: [ส่ง Transactional Email](https://developers.brevo.com/reference/send-transac-email), [ทดสอบโดยไม่ส่งจริง](https://developers.brevo.com/docs/using-sandbox-mode)
